# Meta integration setup and acceptance

This branch adds opt-in sharing summaries, Facebook Page and Instagram professional-account connections, and business messaging through the official Graph API. All four flags default to false. Nothing authorizes a production rollout. Issue #54 remains a prerequisite release gate; its two-user acceptance must pass before merge or production promotion. Existing draft PR #58 is a separate, incomplete foundation and must not be merged alongside this change without reconciliation. This branch starts from main and does not depend on #55, #56 or #57.

## Clerk Facebook Login

Keep the existing Clerk SignIn/SignUp components and Clerk middleware. In the **development Clerk instance**, enable the Facebook social connection. Configure the Meta Facebook Login app with the exact redirect URI shown by Clerk, its App ID and secret, and verified HTTPS application domains. Use the production Clerk instance's own redirect URI and credentials only after acceptance. Do not point Facebook authentication at `/api/meta/callback`: that route authorizes business access for an already authenticated Buddies owner; it never creates a session, links a Buddies identity by Meta email, or replaces Clerk. Clerk remains responsible for verified identity, account linking and session security. Test first-time and returning Facebook sign-in, cancellation, email collisions and unverified provider addresses without refresh. Dashboard configuration cannot be committed as code.

## Environment and staging

1. Use an isolated Preview database and Clerk development instance. Supply the `.env.example` Meta variables through server-side environment configuration. `META_APP_ORIGIN` must be the exact HTTPS Preview origin, without a path. Callback redirects never trust request Host headers.
2. Generate `META_TOKEN_KEY` as base64 of 32 random bytes with a secrets manager. AES-256-GCM uses fresh IVs and binds tokens to owner/platform/asset. Never reuse the Meta app secret as the encryption key. Key rotation requires decrypting/re-encrypting rows under both keys in a controlled maintenance task or disconnecting/reconnecting all assets; replacing the key alone makes stored tokens unreadable. Restrict DB, backup, logs and secret-manager access.
3. Set `META_GRAPH_VERSION` to a version supported by your app and verify all configured endpoints/scopes against current Meta documentation. No runtime default silently advances the version. Meta documentation requests returned HTTP 429 during implementation; live compatibility remains an explicit acceptance blocker.
4. Review the additive migration `20261025103000_meta_social_integration`. It creates only new Meta tables/indexes/foreign keys; it does not change existing data or declarations. Validate the entire migration history on a fresh isolated database, backup and inspect schema drift before applying in Preview. Never use `db push`, reset or the production `build` script for validation. Use `build:ci`, which avoids migration deployment.
5. Enable CORE plus only the needed SHARING/CONNECTIONS/MESSAGING flags in Preview. Keep all flags false in production. Disabling CORE immediately blocks sends, callbacks and shared pages; the signed deauthorization/deletion endpoint remains available for cleanup.

## Meta Developer configuration and permissions

Create a Meta app for the required business use cases. Register the exact HTTPS domain, privacy policy, terms, support contact, app icon and a real data-deletion policy. Set business OAuth redirect URI to `{META_APP_ORIGIN}/api/meta/callback`. No wildcard redirects. Register `{META_APP_ORIGIN}/api/meta/deauthorize` as deauthorization and data-deletion callback; the app verifies Meta's HMAC-SHA256 signed request before erasing provider connections and associated contacts/delivery records. The returned confirmation URL explains deletion; it does not expose identity or provider data. Buddies summaries are separately authored content and can be revoked by their owner; full Buddies account erasure follows the product privacy policy.

Use app roles/test accounts in development. Request advanced access only for capabilities being released, with an App Review screencast showing login, permission consent, asset selection, opt-in messaging and revocation. Complete business verification and any required technology-provider/access verification before third-party business onboarding. Development access does not establish production eligibility.

Incremental connection purposes:

| Purpose | Scopes requested |
| --- | --- |
| Facebook Pages | pages_show_list, pages_read_engagement |
| Instagram professional accounts through Facebook Login | pages_show_list, pages_read_engagement, instagram_basic |
| Facebook Page messaging | Page scopes plus pages_manage_metadata, pages_messaging |
| Instagram messaging | Page/Instagram scopes plus pages_manage_metadata, instagram_manage_messages |
| WhatsApp owned business accounts | business_management, whatsapp_business_management, whatsapp_business_messaging |

No ads, friends, email, personal-feed publishing or content-publishing scopes are requested. Review Meta granular asset permission selection and eligibility for the specific Page/account types. Instagram requires a professional account linked to the authorized Page for this Facebook Login flow. Personal Instagram DMs/posting are unsupported. WhatsApp onboarding currently discovers **owned** WABAs accessible through `/me/businesses`; shared/client WABAs and Embedded Signup are not implemented. Do not market this as general technology-provider onboarding. WhatsApp numbers must already be registered for Cloud API. No secrets or raw tokens are accepted through browser settings.

The callback validates app ID, token validity, granted scopes and conservative expiry through `debug_token`, consumes state atomically, and binds it to both the Clerk-resolved owner and an HTTPS HttpOnly SameSite cookie. Tokens are never included in API responses. Each authorized asset starts paused; review it before enabling. Expired tokens require reconnection; automatic refresh is deliberately absent. Reconnecting replaces its scopes and pauses the asset, so switching from messaging to read-only removes messaging eligibility. Disconnect deletes local token/contact/delivery data. Also revoke access in Meta Business Integrations when you want to revoke the grant at Meta.

## Messaging, consent and webhooks

Configure GET/POST `{META_APP_ORIGIN}/api/meta/webhook` with a random verify token. Subscribe the app to Page/Instagram messaging and WhatsApp `messages` fields in the Meta dashboard. The callback also requests Page/WABA subscriptions. Verify actual signed inbound callbacks for every connected asset: configuration alone is insufficient.

The endpoint caps raw payload size at 64 KiB, verifies X-Hub-Signature-256 before parsing, validates known envelopes, stores a SHA-256 deduplication hash, and updates last-inbound metadata transactionally. It stores no message body. A failed commit returns 503 so Meta can retry. Duplicate/out-of-order events cannot move reply windows forward. Unknown/paused assets are ignored. Echoes and mismatched recipients do not create contacts. Stale callbacks do not reopen messaging. STOP, UNSUBSCRIBE and CANCEL revoke local consent. Add locale-specific opt-out terms before serving other languages. Webhook endpoints must be excluded from interactive login redirects by edge infrastructure; they still require provider signatures.

Settings display only inbound-derived recipient IDs within the owner's connections. The owner must record explicit recipient consent evidence before any send; an inbound message alone is not consent. The sender must explicitly select a dog owned by their Buddies account. Recipients cannot be supplied as arbitrary phone numbers/IDs. Every protected mutation checks Clerk identity, application-user ownership, exact Origin and a database-backed limit of 30 actions per owner per minute; limiter/storage failures fail closed. Use Meta platform rate/quota alerts too. A platform 429 is not automatically retried.

Facebook/Instagram and WhatsApp freeform replies require a verified inbound message within 24 hours. Only approved parameter-free WhatsApp templates listed as `name:language` in `META_WHATSAPP_TEMPLATES` may be sent outside that window through POST `/api/meta/send` with `connectionId`, `contactId`, `senderDogId`, UUID `key`, `template`, and `language`. Do not include `text` in a template request. Submit templates in WhatsApp Manager with the correct language/category, wait for approval, obtain recipient opt-in for the purpose, and verify quality/tier/business restrictions. Variable/media templates and a template-composer UI are not implemented.

A unique owner/connection/idempotency-key hash is persisted before calling Meta. An ambiguous timeout becomes UNKNOWN and is never automatically retried; check the provider inbox before any new send attempt. The settings UI preserves the same key for unchanged retry content. Provider acceptance returns SENT, meaning API acceptance only, not delivery/read confirmation. Delivery/read receipts and a mirrored message inbox are not implemented; use the official business inbox to read message bodies. These business replies do not replace Buddies/Ably messaging.

## Sharing and privacy

Account → Meta connections and sharing offers owned dog profiles/walks and public events hosted by the owner (including public-group checks). Sharing requires explicit consent and creates a random, revocable seven-day summary containing only the dog's name or event title. It never exposes walk time, coordinates, medical data, phone/email or private route IDs. No tracking pixels or Meta SDK load on account/profile pages. Facebook/WhatsApp links open only on user action. Instagram uses the device share sheet, where offered, or copy-link fallback; posting to personal/professional feeds is not implemented. Revocation stops serving the summary; third parties may retain previously copied content or previews.

Retention: run `node scripts/meta-cleanup.mjs` to inspect row counts without deleting. Schedule `node scripts/meta-cleanup.mjs --apply` daily in the selected environment, with its DATABASE_URL explicitly supplied. It deletes expired MetaOAuthState, MetaRateBucket and MetaShare rows, webhook dedup hashes after 30 days, and contacts after 30 days inactivity. Delivery idempotency tombstones are retained until a separately approved retention/retry policy permits deletion. Before rollout, wire and verify this cleanup in the deployment environment; there is no hidden cron installer in this branch. Retain idempotency tombstones for the supported retry period and reconcile UNKNOWN rows with provider evidence. Restrict contacts/consent metadata in backups under the product retention policy.
